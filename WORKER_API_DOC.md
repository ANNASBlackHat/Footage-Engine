# Footage Engine - Job Worker API

Integration reference for any service or script that wants footage search done for
it, without holding a session open and without running the models.

**Verified against** `tests/test_worker.py` (offline, MockEmbedder + InMemoryVectorStore).

---

## 1. What it is, and when to use it

The engine can serve footage search two ways:

| Surface | Shape | Use when |
|---|---|---|
| **MCP server** | Synchronous request/response over stdio/SSE | You are an agent or tool inside a live session, and a human is waiting |
| **Job worker** (this doc) | Async request/response through a database queue | A service submits work and collects it later; the GPU lives on a different machine; the caller is not Python |

Use the worker when any of these is true:

- The caller is **JS / Go / anything** and you do not want a Python client library.
- Search is **GPU-bound** and must run somewhere the models live (a Colab or Kaggle GPU).
- You want the work to **survive** the machine doing it dying.

Do **not** use it for sub-100ms interactive lookups. Every job costs a poll round
trip plus queue latency; `search_footage` itself is ~20-50ms on the fast path once
the model is warm.

---

## 2. The contract in three sentences

1. You need **one shared Postgres database**: the same `DATABASE_URL` for your
   service and for the worker.
2. You submit work by **inserting a row into `jobs`** - three columns: `id`, `task`,
   `payload`. That is the entire producer API.
3. You collect the outcome by **reading `status`, `result`, `error`** from that row.

Nothing else is shared. There is no HTTP endpoint to call, no client library to
install, no protocol to implement, and no port to expose.

---

## 3. The `jobs` table

Generated by `init_db()` from `footage_engine/models/jobs.py`.

```sql
CREATE TABLE jobs (
    id                VARCHAR(36)  NOT NULL,          -- you supply (UUID)
    task              VARCHAR(64)  NOT NULL,          -- you supply
    payload           JSON         NOT NULL,          -- you supply
    status            jobstatus    DEFAULT 'PENDING' NOT NULL,
    result            JSON,
    error             TEXT,
    attempts          INTEGER      DEFAULT 0 NOT NULL,
    backend           VARCHAR(16),                    -- 'qwen' | 'xclip' | NULL = any worker
    idempotency_key   VARCHAR(255),
    picked_by         VARCHAR(128),
    lease_expires_at  TIMESTAMPTZ,
    created_at        TIMESTAMPTZ  DEFAULT now() NOT NULL,
    started_at        TIMESTAMPTZ,
    completed_at      TIMESTAMPTZ,
    PRIMARY KEY (id),
    CONSTRAINT uq_jobs_idempotency_key UNIQUE (idempotency_key)
);
```

The DDL above is the Postgres rendering. On SQLite `status` is `VARCHAR(10)` and
`JSON` columns are `TEXT` - the Python API is identical either way.

| Column | Written by | Notes |
|---|---|---|
| `id` | **you** | `VARCHAR(36)`; any unique string works (`crypto.randomUUID()` is fine) |
| `task` | **you** | One of the five names in section 4; an unknown name fails the job |
| `payload` | **you** | JSON object of task arguments |
| `status` | both | See the state machine in section 7 |
| `result` | worker | JSON, written once, only on success |
| `error` | worker | `"ExceptionType: message"`, truncated to 8000 chars |
| `attempts` | worker | Incremented on every claim. `> 1` means it was retried |
| `backend` | you (optional) | Pins the job to one embedding backend |
| `idempotency_key` | you (optional) | Unique. Makes a retried submit safe |
| `picked_by` | worker | Worker id currently holding the job |
| `lease_expires_at` | worker | After this instant the job can be reclaimed |
| `created_at` | default | Queue order is oldest-first |
| `started_at` | worker | Set on each claim |
| `completed_at` | worker | Set on success or failure |

### Two things that trip people up

**Statuses are stored as enum NAMES - uppercase.** The database holds `'PENDING'`,
`'PROCESSING'`, `'DONE'`, `'FAILED'`, even though the Python API and the CLI report
them lowercase (`'pending'`). Raw SQL must use the uppercase form.

**On Postgres `status` is a native enum type (`jobstatus`), not a string.** So:

```sql
INSERT INTO jobs (id, task, payload, status) VALUES (..., 'PENDING'::jobstatus);  -- explicit insert
INSERT INTO jobs (id, task, payload) VALUES (..., ...);                          -- omit it entirely (recommended)
```

Omitting `status` is simpler and is what the server default is for.

On SQLite, `created_at` is stored as naive UTC text (`2026-09-26 06:00:13`). If you
parse it in JavaScript, note there is no timezone marker - append `Z` or parse as
UTC explicitly, otherwise it will be read as local time. On Postgres the driver
returns a proper timestamp.

## 4. Tasks

Five tasks, named identically to the MCP tools they mirror. Payload keys are the
same too, so an MCP tool call and a job submit are the same request.

### `search_footage` - semantic search

```json
{ "query": "harbour at dawn", "top_k": 5 }
```

| Key | Required | Default | Notes |
|---|---|---|---|
| `query` | yes | - | Natural language |
| `top_k` | no | `10` | Max results |
| `media_type` | no | - | `"video"` or `"image"` |
| `orientation` | no | - | `landscape`/`horizontal` or `portrait`/`vertical` or `square` |
| `min_duration` / `max_duration` | no | - | Seconds |
| `provider` | no | - | `pexels`, `pixabay`, `coverr`, `youtube`, `manual` |
| `entity_name` / `entity_id` | no | - | Scope to a canonical entity |

Result:

```json
{
  "query": "harbour at dawn",
  "count": 1,
  "results": [
    {
      "chunk_id": "b1e...",
      "media_item_id": "7ac...",
      "score": 0.8231,
      "start_ts": 12.5,
      "end_ts": 25.0,
      "duration_sec": 12.5,
      "media_type": "video",
      "orientation": "horizontal",
      "aspect_ratio": "16:9",
      "provider": "pexels",
      "entity_id": null,
      "entity_name": null,
      "storage_url": "https://ik.imagekit.io/.../clip.mp4",
      "source_url": "https://www.pexels.com/video/...",
      "resolution": "1920x1080",
      "license_type": "pexels_free"
    }
  ]
}
```

`storage_url` is what you hand to a video player; `start_ts`/`end_ts` are the cut
points inside it. `count` may be `0` with `results: []` - that is a successful job,
not an error.

### `search_script_beat` - narration beat to B-roll

Decomposes a voiceover sentence into several concrete visual queries, searches all
of them, merges the candidates, and optionally reranks with an LLM judge.

```json
{ "beat_text": "On March 4th, the USS Cyclops vanished into the calm Atlantic.", "top_k": 5, "rerank": true }
```

Accepts the same filter keys as `search_footage`. `beat_text` is required (the keys
`query` and `beat` are accepted as aliases).

| Key | Required | Default | Notes |
|---|---|---|---|
| `beat_text` | yes | - | The narration line |
| `top_k` | no | `10` | Max results after merging |
| `rerank` | no | `false` | LLM judge reorders candidates against the original prose |
| `confidence_floor` | no | - | Drop results scoring below this |

Result adds two keys to the `search_footage` shape:

```json
{ "beat_text": "...", "reranked": true, "count": 3, "results": [ "...same entries..." ] }
```

> **Requires an LLM key on the worker** for expansion and reranking. Without one the
> task still succeeds, but `beat_text` is used verbatim as a single query and no
> entity is detected - so budget for more jobs, or pin `--tasks` accordingly.

### `fine_localize_clip` - refine the cut points

Frame-by-frame scoring inside an already-winning chunk to find the exact sub-window.
This is the most GPU-intensive task: it embeds the query once and then one frame per
sampled frame inside the chunk.

```json
{ "chunk_id": "b1e...", "query": "cargo vessel in storm" }
```

```json
{
  "chunk_id": "b1e...",
  "query": "cargo vessel in storm",
  "original_start_ts": 12.5,
  "original_end_ts": 25.0,
  "refined_start_ts": 14.2,
  "refined_end_ts": 21.8,
  "refined_duration_sec": 7.6
}
```

Typical flow: `search_footage` -> take `chunk_id` -> `fine_localize_clip` -> cut the
clip between `refined_start_ts` and `refined_end_ts`.

> The worker must be able to **download the video** to score frames. If it cannot
> resolve the file it returns `original_*` unchanged - a successful job with no
> refinement. Set `STORAGE_BACKEND=imagekit` (or a remote URL) for remote workers.

### `get_clip_details` - metadata for one chunk

```json
{ "chunk_id": "b1e..." }
```

```json
{
  "chunk_id": "b1e...", "media_item_id": "7ac...", "start_ts": 12.5, "end_ts": 25.0,
  "duration_sec": 12.5, "media_type": "video", "orientation": "horizontal",
  "aspect_ratio": "16:9", "provider": "pexels", "storage_url": "https://...",
  "source_url": "https://...", "resolution": "1920x1080", "license_type": "pexels_free"
}
```

### `get_media_item_details` - one source asset and its chunks

```json
{ "media_item_id": "7ac..." }
```

```json
{
  "id": "7ac...", "provider": "pexels", "source_id": "12345", "source_url": "https://...",
  "media_type": "video", "status": "done", "duration_sec": 145.0, "resolution": "1920x1080",
  "storage_path": "...", "storage_url": "https://...", "chunks_count": 3,
  "chunks": [
    { "chunk_id": "b1e...", "start_ts": 0.0, "end_ts": 12.5, "storage_path": null, "usage_count": 0 }
  ]
}
```

## 5. Submitting from your code

### Python

```python
from footage_engine.worker import (
    submit_search_footage, submit_search_script_beat, submit_fine_localize_clip,
    submit_job, get_job, wait_for_job, count_live_workers,
)

DB = "postgresql://user:pass@host:5432/footage_engine"

# fire and forget
job_id = submit_search_footage("harbour at dawn", top_k=5, database_url=DB, backend="qwen")

# or submit and block
job_id = submit_search_script_beat(
    "On March 4th, the USS Cyclops vanished.",
    top_k=3, rerank=True, database_url=DB, idempotency_key="video-42-beat-7",
)
job = wait_for_job(database_url=DB, job_id=job_id, timeout_sec=300)

if job["status"] == "done":
    for hit in job["result"]["results"]:
        print(hit["chunk_id"], hit["score"], hit["storage_url"], hit["start_ts"], hit["end_ts"])
else:
    print("failed:", job["error"])

# escalate a winner to frame-level precision
job_id = submit_fine_localize_clip(hit["chunk_id"], "harbour at dawn", database_url=DB)

# arbitrary task, useful when you generate payloads dynamically
submit_job("get_clip_details", {"chunk_id": hit["chunk_id"]}, database_url=DB)

# is anything going to pick this up?
print("live workers:", count_live_workers(DB))
```

Signatures:

| Function | Returns |
|---|---|
| `submit_job(task, payload, *, database_url=None, backend=None, idempotency_key=None)` | job id |
| `submit_search_footage(query, *, top_k=10, filters=None, database_url=None, backend=None, idempotency_key=None)` | job id |
| `submit_search_script_beat(beat_text, *, top_k=10, rerank=False, confidence_floor=None, filters=None, ...)` | job id |
| `submit_fine_localize_clip(chunk_id, query, *, database_url=None, backend=None, idempotency_key=None)` | job id |
| `get_job(database_url=None, job_id="")` | job dict or `None` |
| `wait_for_job(database_url=None, job_id="", *, timeout_sec=300.0, poll_interval_sec=1.0)` | job dict; raises `TimeoutError` |
| `count_jobs(database_url=None, *, status=None, task=None, backend=None)` | int |
| `count_live_workers(database_url=None, *, within_sec=None, backend=None)` | int |
| `list_workers(database_url=None, *, within_sec=None, backend=None)` | list of worker dicts |

`filters` is a plain dict using the same keys as the payload (`orientation`,
`media_type`, `provider`, `entity_name`, `min_duration`, `max_duration`).

### JavaScript / Node

```js
import pg from "pg";
import { randomUUID } from "node:crypto";

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });

async function submitSearch(query, { topK = 5, backend = "qwen" } = {}) {
  const id = randomUUID();
  await pool.query(
    `INSERT INTO jobs (id, task, payload, backend) VALUES ($1, $2, $3, $4)`,
    [id, "search_footage", { query, top_k: topK }, backend],
  );
  return id;
}

async function awaitJob(id, { timeoutMs = 300_000, intervalMs = 1000 } = {}) {
  const deadline = Date.now() + timeoutMs;
  for (;;) {
    const { rows } = await pool.query(
      "SELECT status, result, error, attempts FROM jobs WHERE id = $1",
      [id],
    );
    const job = rows[0];
    if (!job) throw new Error(`job ${id} not found`);

    // status is UPPERCASE in the database
    if (job.status === "DONE") return job.result;
    if (job.status === "FAILED") throw new Error(job.error);
    if (Date.now() > deadline) throw new Error(`timeout, still ${job.status}`);

    await new Promise((r) => setTimeout(r, intervalMs));
  }
}

const jobId = await submitSearch("harbour at dawn", { topK: 3 });
const result = await awaitJob(jobId);
for (const hit of result.results) {
  console.log(hit.storage_url, hit.start_ts, hit.end_ts);
}
```

`node-postgres` serialises a JS object parameter into `json` automatically when the
column is `JSON`. If your driver sends it as text, use `$3::json`.

### Any language, SQL only

```sql
-- submit
INSERT INTO jobs (id, task, payload)
VALUES (
  'a1b2c3d4-0000-0000-0000-000000000000',
  'search_footage',
  '{"query": "harbour at dawn", "top_k": 5}'
);

-- poll (status is uppercase)
SELECT status, result, error, attempts
  FROM jobs WHERE id = 'a1b2c3d4-0000-0000-0000-000000000000';

-- cancel something you no longer want (before a worker claims it)
DELETE FROM jobs WHERE id = '...' AND status = 'PENDING';
```

### CLI

```bash
# submit and wait, printing the JSON result
python scripts/submit_job.py --query "harbour at dawn" --top-k 5 --wait

# script beat with reranking
python scripts/submit_job.py --task search_script_beat --beat "..." --rerank --wait

# frame-level refinement
python scripts/submit_job.py --task fine_localize_clip --chunk-id <id> --query "..." --wait

# filters
python scripts/submit_job.py --query "ocean" --orientation portrait --media-type video \
  --min-duration 3 --max-duration 15 --entity-name "USS Cyclops"

# operations
python scripts/submit_job.py --stats
python scripts/run_worker.py --backend qwen --dry-run
```

The CLI exits `0` on success, `1` when the job ends `FAILED`, and `2` on `--wait`
timeout.

## 6. Lifecycle and guarantees

```
   insert                            worker claims                  worker finishes
  ─────────►  PENDING  ──────────────────────────────►  PROCESSING  ──────────►  DONE
                 ▲                                          │                       │
                 │  lease expires (worker died)              │  handler raises       │
                 └──────────────────────────────────────────┘                       ▼
                                                                                  FAILED
```

**Claims are atomic.** A worker wins a job only if a compare-and-swap `UPDATE`
reports a row change, so two workers can never own the same job. `jobs.attempts`
stays at `1` when nothing is double-executed; if you see `2`, the first worker died
and the job was retried.

**Claims carry a lease.** The worker heartbeats and extends `lease_expires_at`. If it
dies - a killed Colab VM, a crash, a hard timeout - the lease lapses and the next
worker reclaims the job. Defaults: lease 900s, heartbeat 30s.

**A failed job stays failed.** It is not retried automatically. Re-submit it (with
the same `idempotency_key` if you want to be safe against duplicates), or reset it:

```sql
UPDATE jobs SET status = 'PENDING', picked_by = NULL, lease_expires_at = NULL, error = NULL
 WHERE id = '...';
```

**Idempotency.** `idempotency_key` is unique, so a retried submit returns the
original job id rather than enqueuing a second one. A good key is deterministic and
scoped to the caller's intent - e.g. `video-42-beat-7`, or
`plan-9-shot-3-localize`. Multiple rows with `idempotency_key = NULL` are allowed.

**Queue order.** Oldest-first by `created_at`. There is no priority.

## 7. Operational rules

**A job waits for a worker.** If none is running, rows sit in `PENDING`
indefinitely - nothing fails. Check before enqueuing if a user is waiting:

```python
from footage_engine.worker import count_live_workers
if count_live_workers(DB, backend="qwen") == 0:
    ...  # start a worker, or tell the user search is unavailable
```

**`backend` pins which worker may take the job.** `qwen` and `xclip` embed into
separate vector collections, so a query embedded by one model must be searched
against the collection that same model wrote. In practice:

| Your footage was indexed with | Set `backend` |
|---|---|
| `EMBEDDING_BACKEND=qwen` (default on GPU workers) | `"qwen"` |
| `EMBEDDING_BACKEND=xclip` (default local) | `"xclip"` |
| unsure | omit it, or run `get_clip_details` on a known chunk |

Mixing them up is the most common cause of "search returns nothing": the query is
embedded into one collection and compared against another.

**Cross-machine search requires a shared vector store.** `VECTOR_STORE=zilliz` for
the worker; the default `in_memory` gives every process a private index, so a remote
worker can search only what it indexed itself.

## 8. Failures and troubleshooting

| Symptom | Cause |
|---|---|
| Job stays `PENDING` forever | No worker is running, or the job's `backend` matches no running worker |
| `FAILED` with `Unknown task '...'` | `task` typo. Valid names are in section 4 |
| `FAILED` with `requires the 'query' payload field` | Missing required payload key |
| `FAILED` with `not found` | Bad `chunk_id` / `media_item_id` |
| `FAILED` with a torch/CUDA error | Model could not load on the worker |
| `DONE` but `count: 0` | Successful search that matched nothing - check `backend`, filters, and that anything is indexed |
| `DONE` but `refined_* == original_*` | `fine_localize_clip` could not download the video |
| `attempts: 2` | The first worker died mid-job; the retry succeeded |
| Timeouts in your caller | Increase your own timeout. `search_script_beat` with `rerank` makes several LLM calls and `fine_localize_clip` scores every frame of a chunk |

## 9. Not supported

Being explicit so nobody builds on a gap:

- **No HTTP/JSON API.** The database is the API. If you need a real endpoint, front
  it yourself or expose the MCP server.
- **No cancel, no priority, no progress percentage.** `PROCESSING` is all you get.
- **No automatic retries or backoff.** A failed job stays failed.
- **No push notifications.** Poll, or add your own `LISTEN/NOTIFY` or webhook.
- **Not a render farm.** Tasks are footage search and metadata only. Ingesting and
  indexing (`ingest_url`, `process_pending_queue`) are MCP-only today.
- **No auth on the queue.** Whoever can reach the database can submit and read jobs.

## 10. Reference

### Worker CLI

```bash
footage-engine-worker                     # console script
python scripts/run_worker.py --backend qwen
python -m footage_engine.worker --backend qwen
```

| Flag | Meaning |
|---|---|
| `--backend {xclip,qwen}` | Which model and collection this worker serves |
| `--tasks A,B` | Allowlist, e.g. `search_footage,fine_localize_clip` |
| `--concurrency N` | Jobs processed in parallel (default 1) |
| `--max-jobs N` | Exit after N jobs |
| `--idle-exit SEC` | Exit after SEC idle seconds; `0` runs forever |
| `--lease-sec N` | Lease duration (must exceed your slowest job) |
| `--heartbeat-sec N` | Lease renewal interval |
| `--poll-interval-sec N` | Empty-queue poll interval |
| `--worker-id ID` | Override the generated id |
| `--mock` | MockEmbedder - no model download |
| `--dry-run` | Config + queue depth, then exit |

### Settings

| Env var | Default | Meaning |
|---|---|---|
| `WORKER_LEASE_SEC` | `900` | How long a claim is owned before it may be reclaimed |
| `WORKER_HEARTBEAT_SEC` | `30` | Lease renewal / liveness interval |
| `WORKER_POLL_INTERVAL_SEC` | `5` | Empty-queue poll interval |
| `WORKER_IDLE_EXIT_SEC` | `0` | `0` = run forever |
| `WORKER_CONCURRENCY` | `1` | Parallel jobs per worker process |
| `WORKER_TASKS` | unset | Default task allowlist |

### `workers` table (read-only for callers)

Written by the worker; useful for liveness checks and a lightweight ops view.

```sql
SELECT id, hostname, backend, device, status, current_job_id, last_heartbeat
  FROM workers
 WHERE last_heartbeat > now() - interval '65 seconds';
```

`device` reports the GPU actually in use, e.g. `cuda (Tesla T4)`. `status` is
`IDLE`, `BUSY`, or `STOPPING` (uppercase, same enum-name rule).
